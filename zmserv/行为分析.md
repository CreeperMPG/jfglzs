# zmserv 行为分析

> 所属家族：机房管理助手（jfglzs13.4）· 组件定位：**看门狗服务（监控主程序，被杀即关机）**
> 分析基于反混淆还原后的代码，非恶意样本运行观察。

## 一、程序概览

`zmserv.exe` 是家族里唯一的 Windows 服务组件，也是唯一的「纯后端」组件：没有窗体、没有托盘、不联网、不读写注册表、不落盘，整个程序只做一件事——**盯着两个进程，两个都不在了就关机**。

| 项 | 值 |
| --- | --- |
| 程序集名 / 根命名空间 | `zmserv` / `zmserv` |
| 输出类型 | `WinExe`，`StartupObject = zmserv.ProcessMonitorService` |
| 目标框架 | .NET Framework `v4.5`，`AnyCPU` |
| 关键引用 | `System.ServiceProcess`、`Microsoft.VisualBasic`、`System.Windows.Forms` |
| 类型 | `ServiceBase` 派生；二进制内服务名 `Service1` |
| 代码规模 | 15 个 `.cs`，唯一业务文件 `ProcessMonitorService.cs`（291 行） |
| 程序集元数据 | `AssemblyTitle`/`Product` = `service`，`Company` = `Microsoft`，`Copyright © Microsoft 2025`，版本 `1.0.0.0`，`Guid 73204acb-20a4-433c-93f1-cd274c4ed922` |
| 反分析 | `[assembly: SuppressIldasm]` 禁 ILDasm；IntelliLock 壳（字符串加密 + IL 补丁写回） |
| 清单 | `app.manifest` 为 `asInvoker`，不提权（权限来自服务账户） |

一句话概括行为面：**除了关机，它没有任何副作用**。

## 二、界面与交互流程

**本组件没有界面。** `OutputType` 虽是 `WinExe`（VB 服务模板的默认值），但 `Main` 第一件事就是 `ServiceBase.Run(...)`，工程里没有 `Form`、没有托盘图标、没有日志输出。它运行在 Session 0，用户「看到」它只有三种方式：服务管理器里的一个条目、任务管理器里的 `zmserv.exe`、以及毫无预兆的黑屏关机。

运行期与外界唯一的交互通道是 **SCM（服务控制管理器）**，完整时序：

1. SCM 按服务的 `ImagePath`（安装时由 `sc create` 写入 `<安装目录>\zmserv.exe`）拉起进程；
2. `Main`（`[MTAThread]`）→ `ServiceBase.Run(new ProcessMonitorService())`，向 SCM 分发器注册；
3. SCM 调 `OnStart`：算当日进程名 → 建 30 秒计时器 → 立即返回（服务进入 Running，用户无感知）；
4. 30 秒后首次检查：见到 `jfglzsn` 才切到 5 秒监视循环；没见到就**静默**地每 30 秒再看一次（不报警、不关机）；
5. 进入监视循环后每 5 秒查一次，连续 16 次（≈80 秒）两个进程都不在 → 关机；
6. 收到停止请求 → `OnStop`：只 `Stop()` + `Dispose()` 两个计时器，无善后、无通知。

停它的标准方式就是 SCM 的三条命令：`net stop zmserv`、`sc stop zmserv`、服务管理器。由于 `OnStop` 不含任何「我停了要不要交代」的逻辑，**服务一停看门狗立即失效**——这正是 `about.exe` / `uninstall.exe` / `przs.exe` 退出流程的第一步。

残留的界面代码只有一处：`Internal/CustomerStrategy.cs` 的 `显示未授权提示()` 会弹 `This assembly is protected by an unregistered version of "IntelliLock"!`（标题 `www.eziriz.com`），但全工程无调用点，且服务进程没有交互桌面，即使被调用也不会显示。

一处需要留意的静态不一致：二进制内 `ServiceName` 被写死为 `Service1`（VB 模板默认值，见 `InitializeComponent`），而家族里所有安装/卸载代码都按 **`zmserv`** 这个名称操作 SCM（见第四节）。按 SCM 规则，分发器里登记的服务名必须与 SCM 中该服务的名字一致，否则启动会以 1083（`ERROR_SERVICE_NOT_IN_EXE`）失败。静态分析无法判定真实环境属于哪种情况，但两种可能都影响排查方式，见第四节第 3 点。

## 三、核心行为

### 3.1 服务启动：一行死路径 + 一个写死的服务名

- 构造函数先给字段 `默认安装目录` 赋 `<盘符>\windows\jf`，**之后从未被读取**（模板/壳残留）；随后 `InitializeComponent()` 建组件容器（`new Container()`）并把 `ServiceName` 设为 `"Service1"`。
- 类里还声明了 `监视间隔毫秒 = 5000`、`启动等待毫秒 = 30000`、`关机特权号 = 19`、`当前线程标志 = 0`、`启用特权标志 = 1`、`关机动作码 = 2` 六个常量，**全部未被引用**，真实数值一律在调用处硬编码。读代码时不要被这些字段误导成「可配置」。

### 3.2 每日一变的受监视进程名

`OnStart` 整段处于 `checked` 上下文（VB 默认溢出检查），流程为：

1. `月日乘积 = Month(Now) * Day(Now)`，取值 1 ~ 372；
2. 先用 `月日乘积 % 7 / % 9 / % 5 / % 3` 四个余数拼一个 4 字母名（`Chr(97+n)`=`a..`、`Chr(98+n)`=`b..`、`Chr(101+n)`=`e..`、`Chr(99+n)`=`c..`），**下一行立刻被整体覆盖**——死代码，但说明作者早期用的是 4 字母名；
3. `VBMath.Randomize(月日乘积)` 播种 → `随机数 = Round(Rnd() * 100000 * 3 + 1)`，取值 1 ~ 300001；
4. 十进制逐位取 `余数 + 105` 转字符（`'i'`=105 … `'r'`=114），前插拼 5 位：结果就是该随机数**低 5 位十进制**的逐位映射（不足 5 位时高位填 `'i'`，即可能出现 `iiimk` 这种带重复字符的名字；把 `i..r` 逆向映射回 `0..9` 就能还原出随机数）；
5. 写入 `受监视进程名`，同时另存 `受监视进程名 + ".exe"`（后者全工程不读）。

两个要点：

- 名字只由「月 × 日」决定，**同一天固定、可提前算出**，每天首次启动服务时变一次。
- 名字只在 `OnStart` 算一次：服务若跨过午夜不重启，记的仍是昨天的名字，而伴生进程当天已换成新名字——此时「随机名」这一路永远匹配不上，判定实际退化为「只看 `jfglzsn`」（静态推断）。也就是说要维持强度，它依赖每天重启一次服务或整机重启。

### 3.3 判定逻辑：两个都不在才算

- **30 秒阶段**（`AutoReset` 计时器）：`Process.GetProcessesByName("jfglzsn")` 有结果 → 建 5 秒计时器并挂 `监视周期检查`，随后 `Dispose` 掉 30 秒计时器；没有结果 → **什么都不做**，30 秒后重试。「开机初期不惩罚」是有意设计：服务先于主程序启动时不能误关机。
- **5 秒阶段**（核心判定）：`GetProcessesByName(受监视进程名)` 与 `GetProcessesByName("jfglzsn")` **同时为空**时才 `连续缺席次数 = checked(连续缺席次数 + 1)`；达到 `>= 16`（≈80 秒）→ 关机；只要任一进程在场，计数立刻清零。

因此它的惩罚目标不是「主程序被关」，而是「整个助手被清干净」：主程序 `jfglzsn` 或当日伴生副本任一存活就不会触发。

### 3.4 强制关机：两条独立的路

命中阈值后依次执行：

1. `ntdll!RtlAdjustPrivilege(19, 1, 0, ref 原状态)`：取 `SeShutdownPrivilege`（19 号特权；第 2 参 `1` = 启用，第 3 参 `0` = 作用于当前线程），**返回值不检查**；
2. `ntdll!NtShutdownSystem(2)`：`1` = 重启、`2` = 关机。这一路**绕过 Win32 关机流程**直接让内核停机，不触发「有程序阻止关机」的常规保护，也不给任何程序保存或否决的机会；
3. 之后再补一枪 `Process.Start("shutdown", "/s /f /t 0")`（`/f` 强关应用、`/t 0` 立即执行；`shutdown` 依 PATH 解析到 `%SystemRoot%\System32\shutdown.exe`）。正常情况下第 2 步已让系统停机，这一句属于「前一步失败时兜底」——两条路都写死，说明作者对「必须关掉」很执着；
4. 同文件另有 `ForceRestart()`（`NtShutdownSystem(1)`），工程内**无调用点**，改一个常量就能变成「重启」；家族其他组件里确实存在「重启整机」的用法（`sc failure … reboot`）。

### 3.5 停止与释放

- `OnStop`：`监视计时器` / `启动等待计时器` 判空后 `Stop()` + `Dispose()`。不写日志、不落盘、不通知，停止后系统上不留任何需要清理的状态。
- `Dispose(bool)`：`try { 释放组件容器 } finally { base.Dispose(disposing) }`，标准模板，无额外逻辑。

### 3.6 壳的运行时行为（非业务，但决定你静态看到什么）

`Internal/` 下三个类属于 IntelliLock（EZIRIZ）壳，没有一条被业务调用，但它们是理解本样本静态视图的钥匙：

| 行为 | 机制 | 影响 |
| --- | --- | --- |
| 字符串解密 | 嵌入资源 `9f3465d1-7736-405a-9581-d615ccfda07a` → AES-CBC 解一层 → 自研「累加 + 混沌 + 异或」流密码解第二层；之后按偏移用 `ReadProcessMemory` 从**本进程模块内存**读密文，再 `AES解密`（写死 32 字节 Key / 16 字节 IV） | 静态看到的是密文；内存 dump 到的也是密文 |
| IL 补丁写回 | 嵌入资源 `08d03c1e-656e-4b82-b230-c3549f0c2ec9` → 解密出补丁流 → `OpenProcess(56, 自己)` + `VirtualProtect(PAGE_READWRITE)` + `WriteProcessMemory` + 恢复原保护 | 「方法体加密」在运行时的还原点 |
| 内嵌 DLL 加载 | `AssemblyResolve` 回调 → 资源名 `b0494a1f-4bd3-` + `Base64(MD5(UTF16(简单名)))` → `Assembly.Load(byte[])`；遇 `FileLoadException` / `BadImageFormatException` 则落到 `%TEMP%\{资源名}\{简单名}.dll` 再 `LoadFile` | 文件系统里看不到的依赖；工程内无调用点（挂事件的模块初始化器在脱壳时被摘掉） |
| FIPS 自适应 | 反射读 `CryptoConfig.AllowOnlyFipsAlgorithms`，按结果在 BCL 实现与自实现 MD5 / AES 之间切换 | 系统启用 FIPS 限制时也能跑，不依赖具体实现 |

补充两点静态确认：两份匿名嵌入资源的名字在 `unpacked\zmserv.exe` 的元数据里能以 UTF-16 字符串形式搜到，但反编译导出的工程只剩 `g.resx` / `Resources.resx` 两份**空模板**（`<data>` 条目数为 0），资源流必须从样本单独导出。另外 `AssemblyInfo.cs` 里 `AssemblyDelaySign(false)`、`AssemblyKeyName` / `AssemblyKeyFile` 均为空 → 程序集**未签名**，`GetPublicKeyToken()` 返回空，于是壳里「用公钥标记覆盖 IV 奇数位再异或密钥」那一步不会生效，派生密钥退化为写死的素材本身——对分析者是好消息，常量可直接使用。

### 3.7 与业务无关的残留代码

- `ILLicenseModule`（`CollectDefinition()`→`true`、`PrintDefinition()`→`false`）、`Internal/ExpressionStrategy.cs`（空 `Attribute`）、各处 `*Definition()` 空桩：IntelliLock 的授权/占位接口，全部无调用点。
- `Internal/ParamsStrategy.cs`、`PolicyStrategy.cs`、`StrategyStrategy.cs`、`TemplateStrategy.cs`、`My/*`：VB 的 `My.Application` / `My.Computer` / `My.User` / `My.WebServices` / `My.Resources` / `My.Settings` 模板转发；`MySettings.settings` 零配置项，两份 resx 零资源。
- `-Module-{799334E8-…}`：CLR 要求的模块占位类型，无成员、无代码。

## 四、与其他组件的关系

zmserv 不是自给自足的组件：它被别人安装、被别人拉起，同时也只监视别人的进程。

| 组件 | 与本服务的关系 | 关键代码 / 命令 |
| --- | --- | --- |
| `set.exe`（管理端） | 安装/重装服务，并设置「失败自动重启」 | 第 13 步 `sc delete zmserv` → 第 19 步 `sc create zmserv binPath= <安装目录>\zmserv.exe start= auto`；紧接 `sc failure zmserv actions= "reboot/60000/reboot/60000/reboot/60000" reset= 300` |
| `jfglzsn.exe`（核心调度） | 6 秒定时器守护服务：`zmserv` 进程不在 → 缺 `zmserv.exe` 就从 `<盘符>\windows\jf\zmserv.dat` 复制 → `sc create` + `net start`；连续救不回伴生进程 5 次时还会 `net stop zmserv` → 重建服务 → 拉起自己的新副本 → `EndApp` 自杀 | `Form1.Timer1`（6 秒）→ `服务守护与自更新` |
| `przs.exe`（驻留小助手） | 自我迁居到 `<盘符>\Program Files (x86)\<当日名第 2~5 位>\<当日名>.exe`；**这个当日名就是 zmserv 监视的第二个进程名** | 同一套 `VBMath.Randomize(月 × 日)` + `Rnd()*100000*3+1` |
| `about.exe` / `uninstall.exe` / `przs.exe` 的退出流程 | 先 `net stop zmserv`，等 3 秒，再杀 `zmserv` 进程；`uninstall` 最后 `sc delete zmserv` | 顺序不能反，否则触发强制关机 |

三点结论：

1. **监视名单的构成**：`jfglzsn`（核心调度）+ 当日名的 `przs` 迁居副本。两者由同一套「月 × 日」算法在各自进程里独立算出名字，所以天然对得上；也正因为算法是确定的，「提前算出今天的进程名」对攻防双方都成立。
2. **闭环**：杀 `jfglzsn` 或杀伴生副本超过 80 秒 → 关机；停服务 → 主程序 6 秒内重建服务；服务崩溃 → SCM 按 `sc failure` 在 60 秒后重启**整机**。所以 README 里「先 `net stop zmserv` 再杀 `jfglzsn`」的顺序是硬要求，单独处理任一环都会失败。
3. **服务名的静态不一致**：二进制内 `ServiceName = "Service1"`，家族全部安装/卸载代码却都用 `zmserv`。若该不一致在真实环境成立，`net start zmserv` 会以 1083 失败，`jfglzsn` 的 6 秒守护就变成「每 6 秒 `sc create` + `net start` 各失败一次」的持续循环（`sc create` 报「服务已存在」，`net start` 报启动失败）；若实机确实能跑起来，则说明部署环节另有覆盖，需动态确认。这条只影响排查与取证方式，不改变「它是看门狗」的判定。

## 五、持久化与配置

**本组件自身不做任何持久化**：不写注册表、不写文件、不建自启动、不联网。它能活下来完全依赖外部组件：

| 持久化点 | 谁写的 | 值 / 位置 |
| --- | --- | --- |
| 服务登记 | `set.exe` 第 19 步、`jfglzsn.exe` 6 秒守护 | `sc create zmserv binPath= <安装目录>\zmserv.exe start= auto`，落到 `HKLM\SYSTEM\CurrentControlSet\Services\zmserv`（`ImagePath` 指向安装目录，启动类型自动；`sc create` 未指定 `obj=`，按默认以 `LocalSystem` 运行） |
| 失败动作 | `set.exe` | `sc failure zmserv actions= "reboot/60000/reboot/60000/reboot/60000" reset= 300` → 服务三次失败内每次 60 秒后重启整机，`reset= 300` 即 300 秒无失败则计数清零 |
| 载荷备份 | `set.exe`、`jfglzsn.exe` | `<盘符>\windows\jf\zmserv.dat`（Hidden + System），`zmserv.exe` 缺失时被复制回去 |
| 删除 | `uninstall.exe` | 先 `net stop zmserv`，卸载末段 `sc delete zmserv` |

> 上表的注册表位置是按 `sc create` 参数推出的（`Services\<服务名>` + `ImagePath` / `Start` / `FailureActions`），不是本组件自己读写的——zmserv 一行注册表代码都没有。

配置项全部硬编码，没有外部可改的开关：

| 项 | 值 | 含义 |
| --- | --- | --- |
| 启动等待 | `30000` ms | 服务启动后首次检查的延迟；未见主程序则继续等 |
| 监视周期 | `5000` ms | 进入监视阶段后的轮询间隔 |
| 缺席阈值 | `16` 次 | ≈80 秒，达到即关机 |
| 主程序进程名 | `jfglzsn` | 写死，不随日期变化 |
| 伴生进程名 | 5 字符，字符集 `'i'`~`'r'` | 由「月 × 日」播种生成，每天变一次 |
| 随机数取值 | `Round(Rnd() * 100000 * 3 + 1)` = 1~300001 | 决定当日 5 位名字（取低 5 位十进制） |
| 关机特权号 | `19` | `SeShutdownPrivilege` |
| 特权调用参数 | `1` / `0` | 启用特权 / 作用于当前线程 |
| 关机与重启动作码 | `2` / `1` | `NtShutdownSystem` 的参数 |
| 兜底关机命令 | `shutdown` + `/s /f /t 0` | 立即强制关机 |
| 服务名（二进制内） | `Service1` | `ServiceBase.ServiceName`，写死在 `InitializeComponent` |
| 服务名（SCM 登记） | `zmserv` | 由 `sc create` 指定，二者不一致（见第四节第 3 点） |
| 残留路径 | `<盘符>\windows\jf` | 构造函数赋值、从未读取；家族数据目录 |

IOC（可用于检索、取证与同族样本比对）：

| 项 | 值 | 含义 |
| --- | --- | --- |
| 服务 | `zmserv`，`ImagePath = <安装目录>\zmserv.exe`，启动类型自动 | 看门狗本体在 SCM 中的登记 |
| 进程（自身） | `zmserv.exe` | 常驻服务进程 |
| 进程（被监视） | `jfglzsn.exe`、`<5 字符>.exe`（`i`~`r` 区间） | 主程序 + 当日伴生副本 |
| 注册表 | `HKLM\SYSTEM\CurrentControlSet\Services\zmserv`（`ImagePath`、`Start`、`FailureActions`） | 服务项，含「失败即重启整机」策略 |

## 六、危害总结

1. **强制关机式惩罚（核心）**：`RtlAdjustPrivilege(19)` + `NtShutdownSystem(2)` 直取内核关机，再以 `shutdown /s /f /t 0` 兜底；无提示、无倒计时、不给保存机会，未保存的作业与文档直接丢失，反复触发还可能损伤文件系统。
2. **剥夺用户对设备的控制权**：服务以 `LocalSystem` 运行，普通用户（学生）无法在不触发关机的前提下结束助手；这不是「保护机器」，而是把「不听话」直接变成关机惩罚。
3. **「清不掉」闭环的关键一环**：`sc failure … reboot` 让服务崩溃也可能演变成整机重启，`jfglzsn` 的 6 秒守护让「删服务」被自动重建——只处理任一个环节都会失败。
4. **反分析设计**：`SuppressIldasm` + IntelliLock（字符串加密、IL 补丁、自读内存）+ 伪装成微软产品（`Company=Microsoft`、`Product=service`）+ 每天变化的进程名，目的都是让人「找不到、也拦不住」。
5. **隐蔽的服务身份**：二进制内服务名 `Service1` 与其恶意用途毫无关联，在服务列表里与系统自带服务难以区分；无 UI、无日志、无网络，行为面极窄，常规主机监控不易告警。
6. **处置要点（顺序不能错）**：先 `net stop zmserv`（或 `sc stop` / 服务管理器）→ 再 `sc delete zmserv` → 再杀 `jfglzsn` 与当日名伴生进程；顺序反了会立刻触发强制关机。同时清掉 `sc failure` 的失败动作与 `<盘符>\windows\jf\zmserv.dat`，否则服务与载荷都会被重建。突破口在 `OnStop`：服务一停，看门狗即刻失效。
